= REST API
:description: Endpoints, request and response formats, headers and status codes of the REST service.

The API is open: there is no authentication yet. Errors are RFC 9457 problem
details (`application/problem+json`) with the types listed under
xref:reference/problem-types.adoc[Problem types].

== Document templates, layouts and revisions

[cols="3,5",options="header"]
|===
|Request |Response

|`GET /templates`
|All document templates and layouts: `id`, `createdAt`, `publishedRevision`,
`latestRevision`.

|`+GET /templates/{id}+`
|One document template or layout with the list of its revisions. The `ETag`
is its latest revision (e.g. `"3"`).

|`+DELETE /templates/{id}+`
|204. Deletes the document template or layout with all revisions. A layout that
a document template still references gives 409.

|`+POST /templates/{id}/revisions+` +
`Content-Type: application/zip`
|201 with `Location` and the released revision. The archive is validated by the
publish checks and released for use in one step; the first revision creates the
document template or layout. A bundle that fails the checks gives 422
`publish-rejected` with every problem, and nothing is stored. With `If-Match`
(the `ETag` of the document template or layout), the upload is stored only if
nobody saved meanwhile, otherwise 412 `revision-conflict`; the response carries
the new `ETag`. +
 +
Files that are already stored as a revision of this document template or layout
give 200 with `Content-Location` and that revision instead of a new one, so an
import can be repeated without changing anything. A layout carries no example
data and is checked with empty data; a document template is checked with its
`example.json`.

|`+GET /templates/{id}/revisions/{n}+`
|The revision (see below).

|`+GET /templates/{id}/revisions/{n}/files+`
|The files of the revision: `path`, `size`, `mediaType`, `sha256`.

|`+GET /templates/{id}/revisions/{n}/files/{path}+`
|One file of the revision, as stored, with its media type.

|`+POST /templates/{id}/revisions+` +
`Content-Type: application/json`
|Saves edited files as a new revision: `{"base": 3, "files": {"template.xhtml":
"…"}, "delete": ["…"]}` is revision `base` with the text `files` written over
it and `delete` removed. Then as the upload of a bundle: validated and released,
201, 200 or 422. `base` must still be the latest revision (or the one
`If-Match` names), otherwise 412 `revision-conflict` and nothing is stored;
`"force": true` saves anyway. +
 +
With binary files — fonts, images, office templates — the same request is
`multipart/form-data`: the JSON in the part `draft`, every file in a part named
after its path (e.g. `fonts/Roboto.ttf`). This also holds for `check` and
`preview` below.

|`+POST /templates/{id}/revisions/{n}/check+` +
`Content-Type: application/json`
|The quick checks of edited files without saving them (`files` and `delete` as
above): every language variant parses, the descriptor and data model are valid,
the layout rules and texts hold, for each listed layout, and every font file
allows embedding. 200 with `problems` (as in a revision) and `warnings`. The
full publish checks run on saving.

|`+POST /templates/{id}/revisions/{n}/vocabulary+` +
`Content-Type: application/json`
|The names edited files may use, for the completion of an editor (`files` and
`delete` as above): `fields` (`path` such as `order.positions[].price`, `type`,
`label`, `description`), `areas`, `components` with their `parameters`, catalog
`styles` with their `kind`, and the keys of the layout's `texts`. For a document
template listing several layouts, only what all of them offer.

|`+GET /templates/{id}/revisions/{n}/bundle+`
|The files of the revision as a ZIP archive.

|`+DELETE /templates/{id}/revisions/{n}+`
|The archived revision. Retires (archives) a released revision, keeping it as
history; a layout revision that a released document template still lists gives
409.
|===

Ids of document templates and layouts consist of lower-case letters, digits and
`-`, at most 64 characters.

Document templates and layouts share these endpoints; the field `kind` tells
them apart: `content` is a document template, `layout` a layout. A bundle with
`layout.json` is a layout; a document template or layout keeps the kind of its
first revision (409 otherwise). A layout is previewed with the render endpoints
like any document template.

A revision of a document template lists the layout revisions named in its
`template.json` (`layouts`, the default first). It is released only if every
listed layout revision is released, and the publish checks render it with each
of them. A layout that a document template lists cannot be deleted, nor can a
listed layout revision be archived (409). `+GET /templates/{id}+` of a layout
lists the revisions of document templates that list it in `usedBy`.

A revision:

[source,json]
----
{
  "template": "invoice",
  "kind": "content",
  "revision": 3,
  "status": "published",
  "layouts": ["corporate@2", "memo@1"],
  "sha256": "854ba28b…",
  "createdAt": "2026-09-19T20:30:08.206936Z",
  "publishedAt": "2026-09-19T20:30:12.010901Z",
  "language": "en",
  "languages": ["de-AT"],
  "formats": ["pdf", "docx", "text"],
  "files": { "template.xhtml": "e3b0c442…", "template.json": "…" },
  "problems": [],
  "warnings": ["field 'notes' is defined but not used by the template"]
}
----

An archived revision also carries `archivedAt`.

=== Bundle

The archive is laid out like the directory of a document template or layout on
the command line, see xref:reference/template-files.adoc[Document template files]:

[cols="2,5",options="header"]
|===
|Path |Content

|`template.xhtml`
|The default variant. Required.

|`template.<tag>.xhtml`
|Language variants.

|`template.json`
|Descriptor with language, formats and field definitions.

|`example.json`
|Example data of a document template. Required to release it: the publish
checks render it with every language variant in every offered format.

|`example/<name>.<ext>`
|Attachments of the example data, referred to as `attachment:<name>`.

|anything else
|Assets: stylesheets, fonts, images, `email.css`, `template.txt`.
|===

A layout bundle holds the files described under
xref:reference/layouts.adoc[Layouts]. A layout carries no example data of its
own; its publish checks render it with empty data.

Limits: 50 MB uncompressed, 1000 files (see
xref:reference/configuration.adoc[Configuration]).

== Schema and validation

[cols="3,5",options="header"]
|===
|Request |Response

|`+GET /templates/{id}/schema+`
|The JSON Schema (`application/schema+json`) of the latest published revision.

|`+GET /templates/{id}/revisions/{n}/schema+`
|The same for any revision.

|`+POST /templates/{id}/validate+` +
`Content-Type: application/json`
|204 if the data is valid, otherwise 422 `invalid-data` with one entry per
violation. Against the latest published revision.

|`+POST /templates/{id}/revisions/{n}/validate+`
|The same against any revision.
|===

A layout may add fields to the data model, so these follow the `layout` query
parameter like rendering (see below); without it, the default layout.

== Rendering

[cols="3,5",options="header"]
|===
|Request |Response

|`+POST /templates/{id}/render+`
|The document, rendered with the latest published revision.

|`+POST /templates/{id}/revisions/{n}/render+`
|The document, rendered with any revision, also an archived one (preview).

|`+POST /templates/{id}/revisions/{n}/preview+` +
`Content-Type: application/json`
|Renders edited files without saving them: `files` and `delete` as for saving,
`data` the data to render (otherwise the edited `example.json`); the example
attachments are attached. Parameters as for rendering.
|===

The data is sent either as `application/json`, or as `multipart/form-data`
with the JSON in the part `data` and each attachment in a part named after it:
the part `photo` is `attachment:photo`.

Layout:: The query parameter `layout`, one of the layouts the revision lists,
as `memo` or `memo@1`; otherwise the default (the first listed). A layout the
revision does not list gives 400 `invalid-request`. The response carries the
layout used in `Template-Layout` (e.g. `memo@1`), next to `Template-Revision`.

Format:: The query parameter `format` (`pdf`, `xhtml`, `email-html`, `text`,
`docx`, `odt`), otherwise the first media type in `Accept` that the document
template offers. `*/*` or no `Accept` gives the first offered format, PDF if offered.
+
[cols="1,3",options="header"]
|===
|Format |Media type

|`pdf` |`application/pdf`
|`xhtml` |`application/xhtml+xml`
|`email-html` |`text/html`
|`text` |`text/plain`
|`docx` |`application/vnd.openxmlformats-officedocument.wordprocessingml.document`
|`odt` |`application/vnd.oasis.opendocument.text`
|===

Language:: The query parameter `lang`, otherwise `Accept-Language`, both as
language ranges (`de-AT, en;q=0.8`). The language variant is chosen by RFC 4647
lookup; without a match, the default variant is rendered. A malformed
`Accept-Language` is ignored, a malformed `lang` gives 400.

Response headers:: `Content-Type`; `Content-Language` with the language of the
rendered language variant; `Vary: Accept, Accept-Language`; `Content-Disposition:
inline` with a file name; `Template-Revision` with the revision number.

Rendering runs in a pool of worker threads with a bounded queue. When the queue
is full, the service answers 503 `overloaded` with `Retry-After` at once.

== Assets

`+GET /assets/{sha256}+` returns an image of a document template or layout (PNG,
JPEG, SVG) by the SHA-256 of its content; `+GET /assets/{sha256}.png+` returns
an SVG as PNG. Both are public and cached as immutable. Email HTML refers to
images this way. Only images are served — language variants, descriptors, fonts
and example data are not.

== Health

`GET /q/health/live` and `GET /q/health/ready`. Readiness waits for the
warm-up: after start, the instance renders the example data of the latest
published revision of every document template in every format before it reports
ready.
