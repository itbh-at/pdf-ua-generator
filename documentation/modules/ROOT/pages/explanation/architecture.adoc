= Architecture
:description: How templates, data, rendering, the CLI and the REST service fit together, and why they are built this way.

This page explains the design of the generator and the reasons behind it. What
is built when is on the xref:project/roadmap.adoc[roadmap].

== The idea in one paragraph

A template is XHTML with Print CSS and Qute expressions. Data is JSON. Qute
renders the template with the data *once*; every output format is produced
from that one rendered XHTML. Templates are not compiled into the application:
they are added, changed and deleted at runtime. Because the build-time checks
Qute normally provides are therefore not available, the generator performs them
itself whenever a template revision is saved, and derives a JSON Schema from
the template so data can be checked before rendering.

== Three modules

[cols="1,3",options="header"]
|===
|Module |Responsibility

|`core`
|Plain Java library, no Quarkus. Template parsing, schema derivation,
validation, rendering, the document model and all format writers. The Qute
engine is configured here and only here, so the CLI and the server render
identically. Templates are looked up through an interface; `core` contains no
database or HTTP code.

|`cli`
|Plain Java and Picocli on top of `core`. Works only with command-line
arguments, files and stdin/stdout. No Quarkus, no database, no network access,
no interactive features.

|`server`
|Quarkus REST service on top of `core`: template store in PostgreSQL, REST API,
security and the editor UI. Until OIDC is added (see the roadmap), every
endpoint is open; run it only where that is acceptable.
|===

Keeping `core` free of Quarkus keeps the CLI small and fast to start, and makes
the rendering behaviour independent of how it is invoked.

== Templates at runtime

Qute can check templates at build time, but only for templates that are part
of the build. Here, editors create templates while the service runs, so that
is not possible. Instead, saving a template revision runs the *publish checks*:

. Qute parses the template; the result must be well-formed XHTML.
. The JSON Schema is derived and compared with the field definitions.
. The template is rendered with its example data.
. veraPDF confirms that the PDF conforms to PDF/UA.

A revision that fails a check cannot be published. These checks are the
replacement for the build-time checks, not an optional extra.

=== Revisions

Every save creates an immutable revision, either a draft or published. Rendering
uses the latest published revision unless a request names a specific one
(`+/templates/{id}/revisions/{n}/render+`), which makes a document reproducible
later and lets editors preview drafts. A revision is a bundle laid out like a
template directory of the CLI, so the same files work in both.

Files are stored once per SHA-256 of their content. A revision's hash covers
its paths and file hashes and is the key of the in-memory cache: a cached
revision can never be stale, and identical revisions share one entry. The
cache holds only the immutable files and what is derived from them (parsed
templates, schema, font metrics); status and other metadata are always read
from the database, so every instance sees the same state. Its size is limited
in bytes, and the least recently used revisions are dropped first.

=== Layouts, components and content templates

[cols="1,1,3",options="header"]
|===
|Kind |Written by |Contents

|Layout
|Developers
|Page format, Print CSS, headers and footers, fonts, named areas
(`+{#insert}+`), the style catalog, and the per-layout files for other formats:
`email.css`, `.dotx` (DOCX) and `.ott` (ODT).

|Component
|Developers
|Reusable blocks as Qute user tags, e.g. columns, box, footnote, signature.
They belong to a layout, which lists them with their parameters in its
`layout.json`.

|Content template
|Editors
|Fills the areas of a layout, using the style catalog and the components.
|===

Content templates are styled only through the *style catalog* — named styles
that exist with the same name in the layout CSS, the `.dotx` and the `.ott` —
and through components. Free choice of font size is the most common cause of
inaccessible documents (a large bold paragraph instead of a heading) and cannot
be mapped to DOCX or ODT. Named styles can.

For emergencies a revision can opt into *free CSS* (`styling: free`) if its
layout allows it. Free CSS works only for PDF and XHTML, keeps hard limits (no
`@import`, no `!important`, only layout fonts, only template assets or
attachments in `url()`), and never bypasses the publish checks.

A content template is one `+{#include layout}+` whose blocks fill the layout's
areas. The layout's files appear to it under `layout/`, so the content cannot
replace them; a layout is checked and previewed the same way, with its own
files under `layout/`. One content template can be rendered in any layout that
offers the areas, styles and components it uses — the demo shows the same
document in two layouts.

The styling rules of content are checked on its source, not on the rendered
document. Data is always escaped and there is no `raw`, so markup can only come
from the literal text of a template: a `<style>`, a `style` attribute or a
class that is not in the source cannot appear in the output. Class values must
be literal for the same reason. Layouts are written by developers and are free
in their markup; their `<style>` may use Qute, so page headers and footers can
take texts from the layout's message files (`+{msg:page}+`) and the document
language from `+{doc:lang}+`.

A content revision pins one layout revision (`corporate@3`). A new layout
revision changes nothing for the content that pins an older one; moving to it
is a new content revision, which re-runs the publish checks. A layout revision
that published content pins cannot be deleted, and content can be published
only with a published layout revision. So a layout change never alters a
published document unnoticed.

== Language variants

A template may exist in several languages, but need not. The default file
(`template.xhtml`) serves every request; optional variants carry a BCP 47 tag
in their name (`template.de-AT.xhtml`). Each variant is a complete template, so
editors can edit every language version on its own; texts that belong to the
layout, such as footer labels, come from the layout's message files per
language.

The API picks the variant from `Accept-Language` with the RFC 4647 lookup; a
`lang` query parameter takes precedence, for example in links sent by email.
Without a matching variant the default is used — a document is always
delivered. Responses name the language in `Content-Language` and declare
`Vary: Accept-Language` for caches. All variants share one JSON Schema, which
the publish check enforces, so a caller never has to know which language will
be rendered. Dates, numbers and currencies are formatted for the selected
language.

== Data and schema

Data is JSON, read into maps and lists that Qute resolves directly. The
syntax tree of a template shows which data it reads and where: a `+{#for}+`
over a value needs a list, `+{a.b}+` needs an object `a`, a value with a default
or read only under a condition is optional. The syntax tree says nothing about
types, so every template also carries *field definitions* with types (text,
number, date, boolean, image, list, object) in its descriptor. Combining the
two gives a real JSON Schema (draft 2020-12) and catches fields the template
reads but does not define, and reads that do not fit the type. The exact rules
are on xref:reference/template-files.adoc[Template files].

Names are resolved statically through `+{#let}+`, loops and includes. `+{#with}+`
is not available: inside it, a name can mean a property of the object or a
top-level value, which only the data decides.

Numbers are JSON numbers, dates ISO 8601 strings. They are formatted in the
template (`+{total.currency('EUR')}+`, `+{due.date('long')}+`) for the language
of the rendered variant, so the data stays language-neutral.

Validation reports every violation with a JSON Pointer to the offending value.
Properties the template does not use are allowed, so callers can send their
existing data objects unchanged.

== Output formats

----
Qute + JSON → XHTML ─┬─ openhtmltopdf → PDF/UA
                     ├─ XHTML (self-contained)
                     ├─ email HTML
                     └─ document model ─┬─ DOCX (StAX + ZIP)
                                        ├─ ODT (StAX + ZIP)
                                        └─ plain text
----

* *PDF* is rendered by openhtmltopdf with PDFBox; target is PDF/UA-1 on PDF 1.7.
* *XHTML* embeds all images and fonts as data URIs, for archiving and preview.
* *Email HTML* uses the layout's `email.css` instead of the Print CSS, inlines
  the styles into `style` attributes, uses absolute image URLs and lays out
  columns and boxes with tables marked `role="presentation"`. Email clients
  such as Gmail do not show data URIs, and Outlook understands little CSS.
* *DOCX, ODT and plain text* are written from a format-neutral document model.
  The model supports a fixed set of building blocks: headings, paragraphs,
  lists, tables with header rows, images, links, emphasis, language changes,
  page breaks, catalog styles, and the blocks `columns`, `col`, `box` and
  `footnote`. Anything else is an error rather than a silent approximation. The
  accessibility checker runs on the model, once for all three formats.
* `multipart/alternative` returns plain text and email HTML from one render,
  in the structure an email needs. The service never sends mail itself.

DOCX and ODT carry the same content, structure and named styles as the PDF,
but not a pixel-identical layout: page breaks and spacing are decided by Word
and LibreOffice.

Their look comes from the layout's Word and ODF templates (`layout.dotx`,
`layout.ott`): styles, default font and page setup, with the layout's fonts
embedded. CSS cannot be translated into Word or ODF styles faithfully; office
templates made in the office applications can express exactly what those
applications offer.

The DOCX and ODT writers are our own code on JDK StAX and ZIP, without an office
library. Both formats are ZIP files with a handful of XML parts, and the
translation from the model is our own code in any case. `docx4j-core` would add
about 25 libraries and a slow start of its XML binding; `docx4j-ImportXHTML` is
tied to an old openhtmltopdf release and says nothing about headings, alt texts
or table headers.

=== Why the writers do not use Qute

Qute is the template engine of the project, so it seems natural to write the
output formats with it as well. It was considered and rejected; the writers are
Java code.

* *Build-time checking is not available where the writers live.* Type-safe
  templates (`@CheckedTemplate`) are checked by the Quarkus build, not by Qute
  itself. The writers belong to `core`, which runs without Quarkus so the CLI
  and the server produce identical output. Moving them to `server` would take
  the formats away from the CLI; making `core` a Quarkus artefact would force
  Quarkus onto the CLI.
* *The compiler already checks more.* The writers switch over the sealed
  building blocks of the document model: a new building block is a compile
  error in every writer that does not handle it. A template would check that
  properties exist, but not that every building block is handled.
* *The work is logic, not markup.* Wrapping text at 72 characters, aligning
  table columns, numbering footnotes, inlining CSS per element and choosing
  image URLs stay Java code either way; templates would hold only the thin
  markup between them, plus a recursive dispatch over the building blocks and
  a value resolver for every model type, because the reflection resolver is
  switched off.
* *XML needs guarantees a text template cannot give.* DOCX, ODT and email HTML
  are written through a StAX writer, which escapes every value and cannot
  produce a document that is not well-formed. A template for WordprocessingML
  would be string assembly again, without that guarantee.

Plain text is the one output that is assembled as a string, because it has no
markup to get wrong.

Running headers and footers with page numbers come from the `@page` margin
boxes of the template CSS (`content: counter(page) " / " counter(pages)`), so
one declaration serves PDF, DOCX and ODT.

PDF/UA requires decorative images to be artifacts, but openhtmltopdf tags every
`<img>` as a figure. Before PDF rendering, decorative images are therefore
replaced by elements that show the image as a background, which openhtmltopdf
marks as an artifact.

Every format is checked automatically (`mise run check-formats`): veraPDF for
the PDF, axe-core for the HTML outputs, the ODF validator for ODT, and
LibreOffice exports DOCX and ODT as PDF/UA for veraPDF.

== Images

Images are PNG, JPEG or SVG. They come from three places:

* *Template assets* (logo, icons) belong to a revision, are stored once per
  content hash and are served publicly at `+/assets/{sha256}+`, so email HTML can
  reference them. SVG assets are also served as a PNG rendition
  (`+/assets/{sha256}.png+`), since many mail clients do not display SVG.
* *Request attachments* are sent as parts of a `multipart/form-data` request;
  the JSON refers to the part and carries the alt text.
* *External URLs* are accepted only from a configured list of hosts. For email
  HTML they are passed through unchanged; for PDF, DOCX and ODT they are
  fetched over HTTPS with strict limits.

Informative images need a non-empty alt text; decorative images are marked as
such. SVG is processed without scripts, external resources or external
entities, and image dimensions are checked before decoding.

== Errors

All API errors are RFC 9457 problem details, produced by the Quarkiverse
extension `quarkus-http-problem`. Validation errors list each violation in an
`errors` member with `detail` and `pointer`. Problem types are URNs, listed on
xref:reference/problem-types.adoc[Problem types].

== Performance

The service keeps everything reusable in memory: parsed templates, compiled
schemas, fonts, font metrics and assets. On start it loads all published
revisions and renders their example data in every format before readiness
reports ready, so a new pod receives traffic only when it is warm. Rendering
runs in a worker pool sized to the CPU cores; when the queue is full the
service answers 503 with `Retry-After`, which lets the autoscaler react instead
of requests timing out.

== Deployment

The service is stateless; all state lives in PostgreSQL. It runs in JVM mode
only — standalone, as an OCI image under podman, or scaled out in Kubernetes.
One Helm chart serves both Kubernetes and `podman kube play` (rendered with
`helm template`); for podman it adds a local PostgreSQL. One
deployment serves one tenant; separate tenants are separate deployments.

== Editor

The editor UI consists of server-rendered Qute pages with htmx. JavaScript is
used only for the two embedded editors: a block editor (TipTap/ProseMirror) for
editors without Qute knowledge, and a code editor (CodeMirror 6) with Qute
support. Diagnostics — Qute and XHTML errors with line and column — come from
the server. Block-edited templates are stored in our own JSON format, not in
the document format of an editor library; `core` translates it into Qute XHTML
and escapes all literal text, so only placeholder nodes produce Qute
expressions.
